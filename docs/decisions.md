# Журнал рішень

Тут записані всі відхилення від плану (промпт у 18 етапів) і пояснення до них.

## D-01 · Повна перебудова замість доробки v0

Попередня версія (тег `v0-microservices`) — мікросервіси: колектори → Redis-черга →
воркер → Postgres/pgvector, дані CoinGecko (знімки кожні 5 хв), три RSS-стрічки,
Fear & Greed, VADER і локальні вбудовування MiniLM (384). Вона не дає того, що
потребує план: годинних свічок з історією від 2025-01-20, частки агресивних
покупок, funding, повних текстів статей. Тому система збудована заново в пакеті
`crypto_rag/`. З v0 перенесено лише практики: конфіг ruff, ізоляцію інтеграційних
тестів від робочої бази, повтори з експоненційною затримкою, healthcheck у compose.

Старий стек працює паралельно (окремий compose-проєкт), доки новий збирач
CoinDesk RSS не запрацює, щоб не втратити дні збору. Статті CoinDesk, які v0
встиг зібрати з RSS, імпортуються в `articles` (channel='rss').

## D-02 · Менеджер залежностей — uv

Швидший за poetry, сам керує версією Python, `uv.lock` фіксує все дерево
залежностей. Версії в `pyproject.toml` записані точно (`==`).

## D-03 · Образ бази `timescale/timescaledb-ha:pg17.11-ts2.31.0`

Офіційний образ Timescale, у якому вже є pgvector (0.8.7). Порт на хості — 5433,
щоб не конфліктувати з базою v0 на 5432.

## D-04 · Інтерфейс на React замість Streamlit

На вимогу автора. Vite + React + TypeScript у `ui/`. Вимога плану зберігається:
інтерфейс звертається лише до API, без прямого доступу до бази.

## D-05 · Режим роботи

Через обмеження в часі (≈3 дні) етапи виконуються підряд без підтвердження
кожного плану. Зупинки — лише там, де план вимагає рішення автора: теги
Guardian, зразок файлу GDELT, ручна розмітка, набір запитань для оцінювання.

## D-06 · Уточнення схеми (етап 2)

- Ціни й обсяги в `candles` / `funding_rates` — `NUMERIC`: рядки Binance
  зберігаються без втрати точності (правило 3).
- `features` — одна колонка `jsonb` (набір ознак змінюється під час
  експериментів, міграції на кожну ознаку не потрібні).
- Цілі прогнозу винесено в окрему таблицю `targets` (вимога етапу 13.2), щоб
  ціль фізично не могла потрапити в рядок ознак.
- `articles.content_hash` і `chunks.content_hash` — щоб повторно обробляти лише
  нові або змінені статті (етап 7).
- `episodes.return_7d_after_pct` — «що було через 7 днів» (етап 9.3).
- `query_log.trace` — повне трасування для `/trace/{id}`.
- `llm_usage` — кожен виклик OpenAI з токенами й вартістю (правило 7).
- Генерована колонка `tsv` використовує `to_tsvector('english'::regconfig, text)`:
  без явного приведення до `regconfig` функція не IMMUTABLE і Postgres її
  відхиляє.

## D-07 · Навчання моделей прогнозу — наприкінці

На рішення автора етапи 13.2–13.5 (LightGBM, GARCH, бектест) виконуються останніми.
Ознаки (13.1) уже будуються щодня; інструмент `get_forecast` без прогнозів у базі
нічого не повертає, і граф пропускає розділ «Прогноз».

## D-08 · CoinDesk RSS розбирається через ElementTree, не feedparser

У стрічці поруч зі справжнім `<description>` стоїть порожній `<dc:description/>`, і
feedparser бере саме порожній — тому v0 вважав, що описів немає. Розбір напряму
повертає опис для всіх 25 записів.

## D-09 · GDELT: DOC API дає неповне покриття

DOC API повертає 5–12 статей CoinDesk на добу і часто відповідає 429; з 20 статей
RSS за тиждень у GDELT знайшлося лише 4. Пробний день архіву GKG дав 24 статті із
заголовками, але повний архів — ≈290 ГБ завантаження. Рішення про архів — за автором.
Час GDELT зберігається як published_at з позначкою `raw.time_source = "gdelt_seen"`;
якщо URL відомий з RSS, рядок RSS має пріоритет.

## D-10 · Уточнення числових інструментів (етап 9)

- Свічка видима лише після закриття (`ts + 1 год <= as_of`).
- `find_similar_episodes`: кандидати закінчуються не пізніше початку поточного вікна;
  результати віддалені один від одного щонайменше на 48 год (інакше top-3 — це та сама
  подія зі зсувом на годину); «що було через 7 днів» показується лише якщо
  `end_ts + 7 днів <= as_of`, інакше це був би витік майбутнього.

## D-11 · Пошук: точне ранжування замість HNSW-сканування з фільтрами

Відфільтрована множина (час, актив, без live blog) матеріалізується й ранжується
точно. HNSW застосовує фільтри після пошуку в індексі й може непомітно повернути менше
за 50 кандидатів. Індекс HNSW лишається для запитів без фільтрів.

## D-12 · Винятки в перевірці чисел (етап 12)

Не вважаються «числами без посилання»: дати, час, роки, тривалості («48 год»,
«7 днів») і числа, дослівно наведені з процитованого фрагмента новини (факти з новин,
а не обчислені системою значення). Правило «кожне обчислене число — з [m…]/[f…]»
не послаблюється.

## D-13 · Доповнення API та розгортання (етапи 14, 16)

- Додаткові ендпоінти `/prices` і `/news` для графіка: інтерфейс не має доступу до бази,
  тож дані для графіка теж ідуть через API. Обидва обмежені `as_of`.
- `/ask` приймає `window_hours` (поле «вікно новин») і повертає `metrics` для карток.
- Окремий одноразовий сервіс `migrate` (`alembic upgrade head`) перед рештою — щоб
  collector, forecaster і api не змагалися за міграції.
- Порти на хості: API — 8001, UI — 8090 (8000 і 8080 зайняті на машині розробки).
- Збої `fapi.binance.com` (funding) не зупиняють оновлення свічок; задача повторюється
  за розкладом.

## D-14 · Теги Guardian — тимчасові

`technology/bitcoin`, `technology/cryptocurrencies`, `technology/ethereum` — до
підтвердження автором за виводом `python -m crypto_rag.ingestion.guardian tags`.
